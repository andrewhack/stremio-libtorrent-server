## The cache budget was counting bytes nobody had downloaded

**A half-finished torrent was charged its finished size.** libtorrent pre-allocates the whole torrent
as a sparse file the moment it is added, so the file's apparent size (`st_size`) is the *final* size
from the very first byte. The evictor summed exactly that, which meant a download still in progress
was billed for data that was not on the disk and might never arrive.

The gap is not marginal. A 60%-complete 80 GiB torrent occupies roughly 48 GiB, and was counted as
80 GiB — a 32 GiB phantom, on a budget that exists to describe disk pressure.

Three things read wrong as a result:

* **`cacheUsed` in `/stats.json`** reported the phantom. Compare it with `du` on the cache root and
  the two disagreed, with no way to tell from the response which one to believe.
* **The "over budget and nothing is evictable" warning** overstated the overshoot by the same amount,
  so an operator sizing a disk from that line was reading a number the filesystem did not recognise.
* **Eviction decisions** were ranked and thresholded on inflated figures. Whole entries could be
  deleted to relieve pressure that did not exist.

**The fix is to charge `min(st_size, st_blocks * 512)`.** `st_blocks` counts the blocks actually
allocated, which is the only figure the disk agrees with. Taking the smaller of the two rather than
`st_blocks` alone matters more than it looks: allocation rounds *up* to the block size, so a
500-byte file would otherwise be billed 4 KiB, and a cache holding many small files would drift the
opposite way. Under-counting slightly is the safe direction for a budget whose entire job is
predicting when the disk fills.

`st_blocks` is POSIX-only. On Windows it is absent and the apparent size is used, which is correct
there — nothing is sparse.

**What changes for you after upgrading.** `cacheUsed` drops to real disk footprint, so a cache that
appeared over budget may simply be under it. Expect *fewer* evictions, not more, and expect the
number to now match `du`. The budget setting itself is unchanged and still means the same thing; it
just finally measures it. Filesystems that compress (ZFS, Btrfs) report post-compression blocks, so
`cacheUsed` there reflects what is genuinely consumed rather than the logical size.

### Also in this release

`connectionTries`, `queued` and `swarmPaused` in `/:infoHash/stats.json` are now documented in the
source as what they have always been: **constants**, carried because the stock server's schema has
them and the client parses the whole object or none of it. libtorrent exposes no equivalent counter.
They are not diagnostics, and a `connectionTries: 0` sitting beside a healthy `swarmSize` means
nothing whatsoever. The fields that do carry peering state are `peers` / `swarmConnections`
(currently connected) and `swarmSize` (known of), alongside `/netcheck.json`.

**Upgrade:** pull it. No new configuration, no route changes, and no change to how bytes are served —
this alters how the cache is measured, not how it is filled or read.
