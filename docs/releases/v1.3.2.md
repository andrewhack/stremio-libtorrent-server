## Sizes and rates can be written as 64GiB instead of 68719476736

Cosmetic release. No behaviour changes to the engine, the API or playback.

**Every size and rate setting now accepts units.** `STREMIOSRV_CACHE_SIZE=64GiB` beats working out
that the number you wanted was 68719476736. This applies to all eight byte-valued settings — the
cache budget, the three rate limits, the playhead readahead, the two adaptive thresholds and the
prefetch ceiling — so the units are consistent wherever a size appears.

Plain byte counts keep working exactly as before. Nothing in an existing `compose.yaml`, `.env` or
appliance image needs to change; that back-compatibility is the first thing the test suite checks.

Two details about the suffixes, because both are silent when misunderstood:

- **`GiB` is binary, `GB` and `G` are decimal.** `64GiB` is 68,719,476,736 bytes. `64G` is
  64,000,000,000 — roughly 4.4 GiB less than most people mean by "64 gig". Prefer the `i` forms.
- **A lowercase `b` does not mean bits.** Parsing is case-insensitive, so `Gb` and `GB` are the same
  thing. This matters most on the rate limits, which are bytes per second, while network speeds are
  usually quoted in bits.

An unparseable value is still a startup error rather than a silent fall back to the default.

**Documentation corrections.** Three tables disagreed with the code: the readahead default is
256 MiB and was listed as 128 MiB, the libtorrent connection cap is 400 and was listed as 200, and
the DEVOPS cache row still advertised a figure from several releases back. All now match what the
server actually does. The Docker Hub overview also drops the TLS appendix, which was pushing the
page against its length limit, and links to the full README on GitHub instead.

**Upgrade:** nothing to do. Pull it if you would rather write your cache budget in gibibytes.
