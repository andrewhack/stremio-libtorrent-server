## Transcoded playback left every segment on disk, forever

**Nothing ever deleted a transcode job directory.** `/destroy` stopped the `ffmpeg` process and left
its output where it lay, and `transcode/` is on the eviction-protected list — so the cache evictor
was forbidden to reclaim it. Between the two, no code path in the server removed a segment.

The volume is the problem. Segments are four seconds long and the playlist is an event playlist, so
`ffmpeg` retains every one it writes rather than rotating a window: roughly **900 files per hour of
transcoded playback**, about 1,800 for a feature-length title. None of them were ever removed. A
single abandoned job directory can outlive months of restarts.

It was also unmeasured. `cacheUsed` sums the entries the evictor manages, and protected names are
excluded from that sum — so segments accumulated while `cacheUsed` still read comfortably under
budget, and nothing in the response accounted for the difference. The disk filled and the server's
own numbers said everything was fine.

**Worth knowing: arriving at the transcoder is not evidence of a codec problem.** A client refuses
direct play for reasons that have nothing to do with what your hardware can decode — notably any file
carrying an embedded subtitle track, or more than one audio track. Such a file is *remuxed*: the
container is rewrapped as HLS without a frame being re-encoded. It still produced the full segment
tree. If your disk was filling while you were sure your clients could decode everything, this is
why. `hlsSessions - hlsReencodes` in `/stats.json` is the remux count.

### What changes

* **Job directories are removed when the job ends.** The server waits for `ffmpeg` to actually exit
  before deleting, because it creates a new file per segment and removing the tree under a live
  process races it. The directory is reclaimed even when no process is tracked, so a `/destroy`
  arriving after a restart still frees the space.
* **A sweep reclaims what `/destroy` never covers** — a killed TV app, a dropped connection, a
  container restart. At startup it runs with no grace, since a fresh process cannot own anything
  already on disk; the periodic pass uses a grace period and always spares a job whose `ffmpeg` is
  still running. Tunable via `STREMIOSRV_TRANSCODE_GC_INTERVAL` and `STREMIOSRV_TRANSCODE_GC_MAX_AGE`.
* **`/stats.json` reports `transcodeUsed`** beside `cacheUsed`. Deliberately reported separately
  rather than folded in: transcode output is not evictable, so adding it to `cacheUsed` would show
  the cache over budget while the evictor correctly declined to act on a protected directory.

Expect a one-off reclaim on first start after upgrading, proportional to how much you have
transcoded since the server was last rebuilt.

### Security: path traversal on the `/hlsv2` routes

The job id and file name in `/hlsv2/<job>/<file>` came straight from the URL and were joined onto the
transcode directory with no containment check. Percent-encoded traversal survives the normalisation
most HTTP clients apply, so an encoded `..` reached the route intact — and because the transcode
directory sits directly beneath the cache root, a crafted request could name **any file stored there,
including the TLS certificate and its private key**, and be served it with a 200.

**Exposure is narrower than that sounds.** The request does not survive the bundled nginx, which
normalises the path so it never reaches the API: the player ports are unaffected. Only the direct API
port is vulnerable, and none of the documented `docker run` or compose configurations publish it. If
you have published that port, bridged it into another container's network, or otherwise exposed it
beyond the host, treat the certificate as disclosed and reissue it after upgrading.

Both path parameters are now validated at a single chokepoint before any filesystem access: separators
and dot segments are refused outright, and the resolved parent is compared against the intended
directory to cover symlinked roots. Malformed requests answer 400. This was found while adding the
directory deletion above — the new code could not be written safely without closing it first.

**Upgrade:** pull it. No new routes, no configuration required, and no change to how bytes are
served — this changes what gets cleaned up and what gets refused, not how streams are fetched or read.
