## Answers the endpoint Stremio's new client asks for — and says honestly that it has nothing to say

`stremio-video` 0.0.93 shipped on 2026-08-12 with four ASS/SSA subtitle changes, and one of them
reaches the streaming server. `stremio-web` already pins it, so this is the client people will be
running, not a preview.

**The new call.** Once per playback whose probe does not rule out an embedded subtitle track, the
client now requests:

```
GET /subtitleSignature?videoUrl=<url>[&container=<format.name>]
    ->  {"error": null, "result": {"signature": <string|null>}}
```

and stores the answer on `videoParams.embeddedSubtitleSignature`. This server had no such route.

**Nothing was broken by that, but it was ugly.** The client wraps the call in an empty `catch`, so
playback was never affected. What it hit was a 404 on port 11470 and — worse — a `200` carrying the
web player's `index.html` on 12470, because the SPA catch-all answers anything it does not
recognise. `resp.json()` threw a parse error once per playback. That is now a clean, parseable
reply.

**The signature is `null`, and that is a decision rather than a placeholder.** There is nothing yet
to compute:

- the reference implementation does not have this route. `server.js` v4.20.16 — the copy published
  at `dl.strem.io`, the one bundled in `tsaridas/stremio-docker:latest`, and the reference kept in
  this repo — contains zero occurrences of `subtitleSignature`, and a running reference server
  answers `404`;
- nothing consumes the value. Neither `stremio-core` nor `stremio-web` mentions it; inside
  `stremio-video` it is only ever produced.

So the algorithm is unspecified, and guessing at one would be worse than returning nothing: the
client accepts *any* string, so a value invented here would start being used the moment a consumer
ships upstream, and subtitles matched wrongly are far harder to diagnose than subtitles not matched
at all. `null` is the client's own documented "nothing here" value, and the branch it already takes.

**It costs nothing at playback start.** No `ffprobe`, no torrent I/O — the handler is constant time,
which matters because the request arrives exactly when the server is busiest serving the stream. It
deliberately does not probe to confirm "there are no embedded subtitle tracks at all", because that
would mean a second uncached subprocess per playback to buy a nicety.

`/stats.json` gains `playback.subtitleSignatureAsks`, counting how often real clients ask. That is
the evidence for when reverse-engineering a genuine signature becomes worth doing. Existing readers
are unaffected — the field is additive.

**Upgrade:** pull it if you use the web player or a current Stremio client; there is no
configuration to change and no behaviour to re-learn. Streaming, seeking, transcode and external
subtitles are untouched by this release.
