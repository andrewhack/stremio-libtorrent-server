## Stops the cache evicting the 4K title you are still watching

A 4K film disappeared from the cache mid-evening, minutes before a TV client fell over, and the log
could not answer the only question that mattered — had it been idle for an hour, or was someone
watching it? It recorded the title and the size, and nothing else:

```
18:39:01  evicted <a 2160p title> (18019.2 MiB)   39.8 -> 21.8 GiB
18:45:01  evicted <a 2160p title> (9365.0 MiB)    35.1 -> 25.7 GiB
```

**The grace window was too short.** Torrents being streamed are protected from eviction — every
byte-range request refreshes a last-served timestamp, and the evictor skips anything served within
`STREMIOSRV_CACHE_EVICT_GRACE`. That protection was never broken. The window was simply narrower
than the gap a 4K player can leave between requests: pull a large chunk, play it back locally, ask
again several minutes later. At 300 seconds, the title on screen could age out of protection while
the cache was over budget — and be deleted under the viewer. The default is now **1800 seconds**.
Space comes back later by the same amount; the sweep still runs every `CACHE_EVICT_INTERVAL`, so
reclaim follows within a minute of the grace expiring.

**Evictions now say what they took and how stale it was.**

```
evicted <title> [<infohash>] (18019.2 MiB, last served 41m ago)
```

`41m ago` is a clean reclaim. `6m ago` means a viewer just lost their stream. `unserved` means the
server never handed that item out at all — a leftover on disk, or something downloaded and never
played. The infohash ties the line to a torrent rather than to a filename.

**Being over budget with nothing to delete is no longer silent.** If every cached item is protected
— by the grace, or by a pin — the pass has nothing to do, and it used to log nothing, so the cache
could sit above its budget indefinitely while the log looked idle and the disk filled. It now warns,
naming how far over budget it is and how much is held. Protecting a stream is the correct call;
hiding it is not. This mattered enough to ship in the same release as the longer grace, which makes
the situation more likely by design.

**Upgrade:** pull it. Nothing to reconfigure — but if your library holds titles larger than about a
third of `STREMIOSRV_CACHE_SIZE`, raise the budget too. A single 18 GB file in a 32 GiB cache leaves
no room for a second one, and the evictor will keep churning whatever the grace is set to.

Also in this release: the repository now carries the `LICENSE` file it had only ever claimed in
prose (MIT, declared in `pyproject.toml` and shipped inside the image), and the DEVOPS configuration
table no longer advertises a 2 GiB cache default against a real 18 GiB.
