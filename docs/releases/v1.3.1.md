## Stops the cache evicting a large title while it is still being watched

Torrents being streamed are protected from eviction: every byte-range request refreshes a
last-served timestamp, and the evictor skips anything served within
`STREMIOSRV_CACHE_EVICT_GRACE`. That protection was never broken. The window was simply narrower
than the gap a high-bitrate player can leave between requests — fetch a large chunk, play it back
locally, ask again several minutes later.

At the old default of 300 seconds, a title being watched could age out of protection while the
cache was over budget, and be deleted underneath the stream. The player then requests a range that
no longer exists. The default is now **1800 seconds**. Reclaim happens correspondingly later; the
sweep still runs every `STREMIOSRV_CACHE_EVICT_INTERVAL`, so space returns within one interval of
the grace expiring.

**Evictions now record what was removed and how stale it was.** The log line gains the infohash and
the time since that torrent was last served:

```
evicted <name> [<infohash>] (<size> MiB, last served 41m ago)
```

A long interval is a clean reclaim. A short one means a viewer just lost their stream. `unserved`
means the server never handed that item out at all — something left on disk, or fetched and never
played. Without those two fields the log could not distinguish the two cases, which is what made
the original report hard to diagnose.

**Being over budget with nothing to delete is no longer silent.** When every cached item is
protected — by the grace window or by a pin — the pass has nothing to do, and it previously logged
nothing at all, so the cache could sit above its budget indefinitely while the log looked idle and
the disk filled. It now emits a warning naming how far over budget it is and how much is held.
Protecting an active stream is the correct behaviour; doing it invisibly is not. This ships in the
same release as the longer grace because a longer grace makes the situation more likely by design.

**Upgrade:** pull it; nothing to reconfigure. If any single file in your cache approaches a third of
`STREMIOSRV_CACHE_SIZE`, consider raising the budget as well — a cache that can hold only one large
title will keep churning no matter how the grace is set.

Also in this release: the repository now carries the `LICENSE` file it had previously only claimed
in prose (MIT, declared in `pyproject.toml` and shipped inside the image), and the DEVOPS
configuration table no longer advertises a 2 GiB cache default against a real 18 GiB.
