## The resume directory has a ceiling now

`.resume/<infohash>.fastresume` is what lets a restart pick up where it left off instead of
rechecking every piece. Less obviously, it also carries the torrent's own metadata — which is why
eviction has always deleted a title's data and its `.parts` holding file and left the record alone.
Re-playing something the cache dropped months ago gets its file list straight out of the record
rather than waiting on the swarm for it, and that is worth far more than the few kilobytes it costs.

What was missing was a ceiling. Nothing removed a record except the library's own Remove button, so
the directory accumulated one entry per torrent ever added, forever, and the name index beside it
grew in lockstep — on a real box, 138 of 141 entries described titles that had left the cache
months earlier. A failed atomic write from two months back was still sitting there too, because
nothing swept those either.

A daily pass now retires records nothing claims any more, with a default cutoff of one year.
Anything the server still claims — the data is in the cache, the title is kept, or a download wants
it — is exempt regardless of age. That order is the whole design, and inverting it would be wrong
rather than merely cruder: only kept and wanted torrents are re-added to the session at startup, so
a title that is sitting in the cache but not loaded has a record as stale-looking as any orphan's.
Age on its own would delete exactly the metadata most likely to be needed next.

The cutoff is deliberately generous. A record averages tens of kilobytes and a busy server adds a
couple a day, so a year of them is a few tens of megabytes — this bounds the directory, it does not
tidy it, and every record deleted early is a metadata fetch someone pays for later. Set
`STREMIOSRV_RESUME_RETENTION_DAYS` to change the horizon, or to `0` to keep everything as before.
The same pass reclaims `.tmp` files left by interrupted writes, and retires an index entry when the
record it describes goes — the two share a lifetime because the entry exists to name the record.

**Upgrade:** pull it. No configuration changes required and no route changes.
