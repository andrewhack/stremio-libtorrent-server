## One evictor per cache root, and three ways a kept file could still vanish

**Two servers sharing one cache directory delete each other's data.** Each protects only what its
own libtorrent session holds a handle for, and each enforces its own budget — so the smaller budget
reclaims the larger server's cache wholesale, and every entry goes out looking like something
nothing ever asked for:

```
evicted <name> [no-handle] (<size> MiB, last served unserved)
```

That is simply what a whole cache looks like to a server that has just started: it holds no handle
for a file it did not download, so nothing is in use, and nothing is pinned either. `run_evictor`
now claims the root through a heartbeat file and holds off while another server's claim is live.
Three details matter more than the claim itself. The claim self-expires, so a container that dies
never wedges eviction. A container's own previous process is recognised by hostname rather than
mistaken for a rival — otherwise the survivor of a restart locks itself out of its own cache. And
the check runs every cycle rather than once at startup, because giving up permanently turns a few
minutes of overlap into an evictor that never runs again, leaving a cache stuck over budget with
nothing in the log to say why.

**A pin only protected a live handle.** Protection was built from the torrents currently loaded in
the session, so a pin stopped protecting anything the moment its torrent was not loaded — and a
finished download, which nothing writes to any more, carries the oldest timestamp in the cache and
is therefore first in line the instant that happens. The registry that survives restarts is now
consulted directly. That includes pins which never recorded a name, because they were made from a
magnet before its metadata arrived: the persisted name index knows what the registry does not.

**Partfiles were protected by nothing at all.** libtorrent's `.<infohash>.parts` holding file is a
cache entry in its own right, and its name can never equal a torrent's, so every name-based
protection missed it — which is why they always went out unattributed. Deleting one throws away the
partial pieces of a torrent that had just been decided to keep. A partfile now inherits its
torrent's protection, and is removed *with* its torrent, so a reclaim no longer leaves an orphan
that nothing will ever claim.

**And the sweep ran at half its advertised rate**, sleeping once at the top of its loop and again at
the bottom: the startup line said one interval and the loop took two. The transcode sweep had a
related edge — it read the clock once before its loop, so a job directory stamped a moment later
carried a negative age and was skipped by the very pass documented as taking no grace.

### Experimental

`STREMIOSRV_LIBRARY_UI` (default `false`) turns on a browser page for managing what the server is
holding. It is unfinished, its shape will change between releases, and it is off unless you set it.
If you do not set it, this release is exactly the paragraphs above and nothing else.

**Upgrade:** pull it. No configuration changes and no route changes on the default surface — the
new routes exist only while the experimental flag is on.
