## A stream that ends early now says which torrent, and where it stopped

**The warning an aborted playback leaves behind identified a piece, but not the thing the piece
belonged to.** `piece <n> not available within 30s (peer-starved?); ending stream` gives a piece
index in a torrent it does not name, at an offset it does not report. On a server with more than one
title in its cache, two such lines are indistinguishable: you cannot tell whether one stream starved
twice or two streams starved once, nor whether the stall landed where a viewer had just seeked to or
somewhere the player was already streaming through.

Both stream-ending warnings now carry the infohash, the file index within the torrent, the byte the
read had reached, the range the client asked for, and how many bytes were actually served:

```
piece <n>/<total> not available within 30s (peer-starved?); ending stream
  [<infohash> file <i>, byte <offset> of range <start>-<end>, <k> served]
```

`<k> served` is the field to read first. **Zero** means the stall was at the requested offset — the
very piece the player asked for never arrived, which is what a seek into a cold region looks like.
**Non-zero** means bytes flowed and the window ran dry partway through, so the budget that expired
was the shorter mid-stream one rather than the longer first-piece one. That one number separates "the
swarm cannot reach this torrent" from "the swarm cannot keep up with this playback", and those have
different fixes.

The infohash is handed to the file server by the route rather than read back off the torrent handle.
That looks like the long way round, and the reason is the same one that keeps the read cursor in the
route: this generator must never raise into the ASGI layer, and asking a handle for its status is one
more call that can fail on a handle the evictor has just removed — precisely the moment the log
matters most.

**The two piece-wait budgets are configuration now.** `STREMIOSRV_STREAM_PIECE_TIMEOUT` (default 30
seconds) is how long a request waits for a piece mid-stream. `STREMIOSRV_STREAM_FIRST_PIECE_TIMEOUT`
(default 120) covers the first piece of a request, which is always a cold start — the beginning of
playback, or a seek into a region nothing has downloaded yet. Both already existed as parameters
carrying those defaults, but the route passed neither, so they were constants nothing could reach.

Worth knowing before raising the first one: it cuts both ways. When the piece is merely late — a slow
or thinly-peered swarm — waiting it out beats an interruption. When the piece is never coming, that
number is exactly how long playback freezes before the retry that would have recovered it. The
enriched warning above is what tells you which case you are in.

**Upgrade:** pull it. Defaults are unchanged, so a server that sets neither variable behaves exactly
as 1.3.3 did.
