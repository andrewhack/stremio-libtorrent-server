## The captured reference moves to server.js v4.21.1

**Upstream shipped five releases and the contract did not move.** This server is a reimplementation
of Stremio's streaming server, and the thing it is measured against is a captured copy of the
official bundle — pinned in `docs/server-url.txt`, mapped route by route in `docs/protocol-map.md`.
That copy had been v4.20.16 (January 2026) while upstream went on to publish v4.20.17, v4.20.18,
v4.20.19, v4.21.0 and v4.21.1 (August 2026). Being five releases behind the reference is not a
comfortable place to make parity claims from, so the bundle was re-captured and re-diffed.

**One route changed, and no client can reach it.** Comparing every route registration in v4.20.16
against v4.21.1 turns up a single addition — a downloader namespace introduced in v4.20.18:

```js
process.env.SERVER_IPC_KEY && enginefs.router.use(
    `/${process.env.SERVER_IPC_KEY}/downloader`, downloader)
```

The mount is conditional. With `SERVER_IPC_KEY` unset the six routes under it do not exist at all,
which is how the common Docker packaging runs the official server; and a browser client has no way
to learn a secret that lives only in the server process's environment. It is also not what the name
suggests to anyone reading it from here: it drives `node-downloader-helper`, a plain HTTP file
downloader with `add?url=`, `pause`/`resume`/`remove?id=` and records persisted to `downManager.json`
— no torrents anywhere in it.

**Nothing was removed and no response shape moved.** Every claim this project makes about the
reference still holds word for word against v4.21.1: `/subtitleSignature` is still a route the
official server does not define, and `/opensubHash`, the `hlsv2` family, `/cache.json` and the
hardware-acceleration surface are all unchanged. The remaining differences between the two bundles
are internal — an iOS embedding bridge replacing the Android one, and a rewritten free-space probe
feeding the cache evictor — neither of which is addressable over HTTP.

**What changes for you: one string.** `/settings` now reports `serverVersion: "4.21.1"` instead of
`"4.20.16"`. That field exists because native shells version-gate the streaming server they are
configured against and fall back to their own bundled one if the answer does not look like a real
Stremio server, so it has to name a real version — and naming the version whose routes have actually
been diffed is the honest answer. Player-side the field is inert: `@stremio/stremio-video` 0.0.96
contains no reference to `serverVersion` at all.

**Verified against a real client, not just a diff.** The protocol drift probe drives an unmodified
`stremio-web` build through this server end to end. Its most recent run against the current
development client reports playback ok and no new, removed or failing request templates — the same
verdict it gave before this change, which is the point: a reference update that altered behaviour
would not be a reference update.

**Upgrade:** pull it. No new configuration, no route changes, no behaviour change to playback,
caching or transcoding. The only observable difference is the version string in `/settings`, and the
only reason to care about it is that parity statements now cite a bundle from August rather than
January.
