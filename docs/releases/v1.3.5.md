## `/stats.json` now says what the transcode path is actually costing

**Nothing reported hlsv2 at all.** `/stats.json` covered stalls, piece timeouts and prefetch arms —
the read path — while the transcode path was invisible. You could see a server struggling to feed a
direct-play stream, and see nothing whatsoever about how often it was starting ffmpeg instead.

Two new counters:

```
"playback": { …, "hlsSessions": <n>, "hlsReencodes": <k> }
```

**Two numbers rather than one, because landing on `/hlsv2` is not evidence of a codec problem.** A
client decides for itself whether to direct-play, and it refuses for reasons that have nothing to do
with what this server can serve. The clearest example: `stremio-video` ANDs `!hasEmbeddedSubtitles`
into its `canPlay` check, so **any** file carrying an embedded subtitle track is sent here — the
subtitle codec and the container are both irrelevant. Perfectly playable H.264/AAC then arrives only
to be repackaged.

The transcode planner already decides per stream whether to `copy` or convert, so the split is free.
A job whose every stream says `copy` is a **remux**: the container is rewrapped as HLS and not one
frame is re-encoded. `hlsReencodes` counts the other kind, where at least one stream is genuinely
converted — an unsupported codec, too many audio channels, or a frame wider than the cap.

So `hlsSessions - hlsReencodes` is the remux count, and the two shapes read very differently:

* **sessions climbing, re-encodes near zero** — the box is repackaging, not converting. Cheap. Raising
  transcode capacity would buy nothing.
* **re-encodes tracking sessions closely** — that is real CPU or GPU, and worth acting on.

**These count jobs, not requests.** A player re-fetches `master.m3u8` several times during one
playback, so the counter sits behind the check that reuses a job already running. Counting the route
would have multiplied a single playback into several.

**Upgrade:** pull it. No new configuration, no route changes, and no behaviour change to playback —
this only adds two integers to a response that already existed. Like the other counters they are
process-local and reset when the container restarts, so read them after a stretch of normal use
rather than immediately after a deploy.
